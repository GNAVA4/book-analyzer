## Формальная модель (единый механизм для всех сценариев)
1. Документ → абзацы → **атомарные утверждения** (claims).
2. Мягкое сопоставление утверждений по смыслу (эмбеддинг-близость + проверка «то же самое»).
3. Операции над множествами утверждений. Меняется только выбор **C (корпус, точка 0)** и **E (эталон, точка 1)**.

nov(X) = утверждения X, отсутствующие в C (после дедупликации внутри X).
- **Покрытие** = |nov(D) ∩~ nov(E)| / |nov(E)|  ∈ [0, 1]
- **Сверх эталона** = |nov(D) \~ nov(E)| / |nov(E)|  ∈ [0, ∞)
- Выдаём **ДВА числа** [user]. Сумма N = покрытие + сверх — максимум как справочная.
- 0 = ничего нового относительно C; 1 = новизна та же, что у эталона; >1 = есть своя новизна.
- Важен и сам список фрагментов новизны (что именно нового), не только числа.

### Сценарии
- **A — курсовые** [supervisor]: C = методичка + лекции + база; E = образцовая курсовая; D = проверяемые курсовые.
  Самый чистый полигон для проверки формулы. Материалы user может найти.
- **B — мивары** [supervisor]: (1) C = прежние работы (сборники прошлых лет / остальные статьи сборника) →
  «типовость, пишут ли по шаблону»; (2) E = что сказала бы нейросеть на ту же тему → «у кого полезнее».
  ⚠️ Модели только локальные [user] → эталон от qwen-7B слабый (о миварах почти ничего не знает).
  B(2) отложен до появления сильной модели; B(1) делаем.
- **C — роль абзаца** [supervisor]: продвижение к цели статьи vs анонс / связка / цитирование / повтор.
  Даёт веса утверждениям и меру «воды». Расширение: ценность мысли за пределами статьи (субъективно).
- **D — широкие критерии** (логичность, доказательность, понятность, полнота, рекомендации, поиск/рейтинг)
  [supervisor] — LLM-as-judge по рубрике. ОТЛОЖЕНО до работающего ядра (риск расползания темы).

### Фаза 1a — структура одиночной статьи без оглавления (входной слой)
**Решение [user, 2026-10-17]:** под сборник отдельную архитектуру НЕ делаем. Статьи загружаются
ПООДИНОЧКЕ (сборник при необходимости режется на отдельные PDF вне системы). Проблема — у статьи нет
оглавления → структуру нужно восстановить.

Ключевое: для анализа разделы НЕ обязательны (единица = абзац/утверждение). Структура нужна для
(а) вырезания шума (шапка, литература), (б) агрегации по разделам, (в) сценария C (цель статьи).

Каскад «дешёвое → дорогое» (как ToC-каскад этапа 1):
1. **Якорные блоки по словарю** (регэкспы, без моделей): «Аннотация/Abstract», «Ключевые слова»,
   «Введение», «Заключение/Выводы», «Список литературы/Литература/Библиографический список/References»,
   УДК/DOI. Русские научные статьи довольно стандартны.
2. **Заголовки по вёрстке**: PyMuPDF spans — размер шрифта/жирность/отдельная короткая строка,
   нумерация «1.», «2.1». По сути СИНТЕЗ ОГЛАВЛЕНИЯ из вёрстки, причём сразу с точными позициями →
   mapping по тексту не нужен (в отличие от книг).
3. **Смысловые границы** (эмбеддинги соседних окон, TextTiling-подобно) — если заголовков нет
   (короткие тезисы). Опционально.
4. **LLM** — последним, для неоднозначного. (В этапе 1 есть уровень deep_scan — LLM по чанкам — можно
   переиспользовать идею.)
Если структуры нет вовсе — статья = шапка + тело (абзацы) + литература; анализ всё равно работает.

**Список литературы:** вырезать из тела для анализа новизны (иначе шум), но сохранить как метаданные
(пересечение ссылок между статьями — дешёвый сигнал шаблонности).
Выход: тот же XML-формат дерева, что у книг (совместимость со слоем анализа).
→ verify: на 5–10 статьях блоки (шапка/аннотация/разделы/литература) совпадают с PDF (ручная сверка).

**Статус (session 014):** ✅ прототип `app/services/article_parser.py`, 5/5 статей разобраны
